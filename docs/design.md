# COBOL ATM 詳細設計書

版数 1.0 / 2026-09-17

---

## 1. 目的と範囲

現金自動預払機 (ATM) の端末側アプリケーションを COBOL で実装する。
勘定系ホストは持たず、口座元帳を索引編成ファイルとして端末側に置く
構成とする。ホスト接続へ移行する場合は `ATMACCT` の差し替えだけで
済むよう、口座 I/O を 1 モジュールに封じ込めている。

**範囲内**: 認証 (磁気 / IC / 生体)、残高照会、出金、入金、振替
(自行・他行)、暗証番号変更、金種計算、カセット在庫管理、
電子ジャーナル、限度額管理、取引取消、営業日カレンダー、日次締め。

**範囲外**: 通帳記帳、キャッシュカード発行、係員操作パネル。

**画面**: コンソール 1 系統のみ。画面数を絞る代わりに、取引の
順序制御・例外処理は実機と同じ規律を保つ。

## 2. モジュール構成

```
ATMMAIN  端末制御 (セッション/画面遷移/取引順序制御)
  ├─ ATMAUTH  カード認証・PIN・カード閉塞・限度額・当日累計
  │    ├─ atmcard.dat   カードマスタ (索引編成)
  │    └─ atmlimit.dat  限度額マスタ (媒体 × 認証方式)
  ├─ ATMPOST  取引記帳 (検証順序/手数料/残高更新/補償)
  │    ├─ atmfee.dat    手数料マスタ (曜日区分 × 時間帯 × カード区分)
  │    ├─ ATMACCT  口座マスタアクセス (排他制御)
  │    │    └─ atmacct.dat  口座マスタ (索引編成)
  │    ├─ ATMAUTH  (限度額判定・当日累計更新)
  │    ├─ ATMCAL   (曜日区分)
  │    └─ ATMZGN   (他行あて為替)
  │         ├─ atmbank.dat  金融機関マスタ (索引編成)
  │         └─ ATMCAL       (営業日・翌営業日)
  ├─ ATMCASH  紙幣払出・入金収納・カセット在庫
  │    └─ atmcash.dat   現金カセット (索引編成)
  ├─ ATMCAL   営業日カレンダー (曜日区分・祝日・翌営業日)
  │    └─ atmhol.dat    祝日マスタ (順編成)
  └─ ATMJRNL  電子ジャーナル出力 (追記専用)
       └─ atmjrnl.dat   EJ (順編成)

ATMCLS   端末状態 (締め状態・連番の採番)
  └─ atmclose.dat  締め状態 (索引編成)

ATMDAY   日次締めバッチ (端末停止中に流す)
  ├─ ATMCLS   (締めてよいかの判定・締めの記録)
  ├─ ATMJRNL  (EJ 走査)
  ├─ ATMCASH  (帳簿照会・当日計の繰越)
  └─ ATMRPT   締めレポート出力
       └─ atmrpt.txt   帳票 (行順編成)

ATMSEED  試験用マスタ初期作成 (運用バッチ相当)
CALTEST  ATMCAL 単体ドライバ (固定日を与える回帰テスト)
ZGNTEST  ATMZGN 単体ドライバ (固定日時を与える回帰テスト)
```

時刻に依存するモジュールは専用ドライバで検証する。実行日ごとに
結果が変わると回帰テストとして成立しないため。

### 呼出規約

| 規約 | 内容 |
| --- | --- |
| 第 1 引数 | モジュール固有パラメタ (機能コード + 入出力域) |
| 第 2 引数 | `ATM-SESSION` (セッション共有域) |
| 終了 | 下位モジュールは `STOP RUN` せず `GOBACK` のみ |
| 責務 | 下位モジュールは自分の責務範囲の項目だけを更新する |
| ファイル | 1 ファイルの `FD` を持つのは 1 モジュールのみ |
| ロック | `UNLOCK` は取引単位、`CLOSE` は端末単位 |
| 業務判定 | I/O モジュールは技術的な結果のみ返す。業務判定は `ATMPOST` が持つ |
| 取引属性 | 営業日・時刻・曜日区分は `ATMMAIN` が取引開始時に確定し、下位は読むだけ |
| マスタ | 順編成の参照マスタは起動時に一度だけ全件読む。不在時は空テーブルで続行する |

## 3. データ設計

### 3.1 口座マスタ (`ACCTREC.cpy` / 160 バイト / 主キー `ACCT-NO`)

| 項目 | 形式 | 備考 |
| --- | --- | --- |
| `ACCT-NO` | X(10) | 主キー |
| `ACCT-STATUS` | X(1) | N 正常 / F 凍結 / D 休眠 / X 解約 |
| `ACCT-LEDGER-BAL` | S9(13)V99 | 元帳残高 |
| `ACCT-AVAILABLE-BAL` | S9(13)V99 | 支払可能残高 |
| `ACCT-HOLD-AMT` | S9(13)V99 | 保留額 (将来拡張) |
| `ACCT-OVERDRAFT-LIMIT` | S9(13)V99 | 当座貸越枠 |
| `ACCT-VERSION` | 9(9) | 楽観ロック用 |

**元帳残高と支払可能残高を分離する理由**: ATM 取引は即時反映のため
現状は両者が一致する。将来、未決済入金や差押えによる保留を導入した
際に、残高計算式だけを変えれば済むようにしている。

**金額を表示形式 (`SIGN LEADING SEPARATE`) にした理由**: 障害解析時に
データファイルをそのまま読めることを優先した。COMP-3 は容量効率で
勝るが、端末 1 台あたりの口座数は高々数万件で圧迫要因にならない。

### 3.2 カードマスタ (`CARDREC.cpy` / 160 バイト / 主キー `CARD-PAN`)

PIN は平文で持たず、カードごとのソルトとの合成値をハッシュして
保持する。当日累計 (`CARD-DAILY-*`) のほか、媒体 (磁気 / IC)、
生体認証の登録有無、発行区分 (自行 / 提携) を持つ。

カードの `CARD-LIMIT-*` は顧客が設定した上限で、銀行が定める上限
(限度額マスタ) との小さい方が実効値になる (§6.5)。

### 3.3 現金カセット (`CASHREC.cpy` / 120 バイト / 主キー `CASH-ATM-ID`)

4 カセット固定。各カセットに金種・枚数・ニアエンド閾値・状態を持つ。

### 3.4 参照マスタ (順編成 / 起動時に全件読込)

| ファイル | 内容 | 所有モジュール |
| --- | --- | --- |
| `atmfee.dat` | 手数料 (曜日区分 × 時間帯 × カード区分 × 取引種別) | `ATMPOST` |
| `atmlimit.dat` | 限度額 (媒体 × 認証方式) | `ATMAUTH` |
| `atmhol.dat` | 祝日 (昇順。二分探索で引く) | `ATMCAL` |
| `atmbank.dat` | 金融機関 (索引編成。都度キー引き) | `ATMZGN` |

前 3 者は取引のたびに引く小さな表なので、起動時に一度だけ読んで
メモリに載せる。マスタが無い場合は空テーブルのまま続行する
(手数料ゼロ、限度額は 9003 で取引不成立)。

金融機関マスタだけ索引編成にしてあるのは、件数が伸びうるうえ
他行あて振込 1 件につき 1 行しか要らないため。

### 3.5 電子ジャーナル (`JRNLREC.cpy` / 200 バイト / 順編成・追記専用)

1 取引につき最低 2 レコード (`S` 開始 / `E` 終了) を出力する。
取消が発生した場合は `R` を挟む。

**`E` が無い取引は「不確定取引」**。電源断や異常終了で発生する。
日次バッチがこれを抽出し、現金カセットの実査と突合して補正する。

## 4. 取引シーケンス

### 4.1 出金 (最重要)

```
ATMMAIN                ATMCASH        ATMPOST         ATMAUTH   ATMACCT
   │
   ├─ EJ(S) ───────────────────────────────────────────────────────►
   ├─ PLAN ──────────►│ DP で金種構成を算出 (在庫は減らさない)
   │                  │  不成立 → 4001/4002 で取引終了
   ├─ WITHDRAW ──────────────────►│ 金額検証 → 営業時間 → 手数料
   │                              ├─ LIMITCHK ─────►│ 限度額 3 段判定
   │                              ├─ READLOCK ───────────────────►│
   │                              │  支払可能残高 + 貸越枠 と比較
   │                              ├─ UPDATE ─────────────────────►│
   │                              └─ ADDDAILY ─────►│ 当日累計加算
   ├─ DISPENSE ──────►│ 在庫再検証 → 減算 → REWRITE
   │                  │  失敗 → REVERSE で記帳を戻し EJ(R) を出力
   └─ EJ(E) ───────────────────────────────────────────────────────►
```

**なぜ金種計画を記帳より前に行うか**: 逆順にすると「記帳は済んだが
紙幣が出せない」状態が発生し、必ず取消処理が要る。取消は失敗し得る
ので、そもそも発生させない順序を選ぶ。

**なぜ PLAN と DISPENSE を分けるか**: PLAN 時点で在庫を押さえると、
記帳が失敗したときに在庫を戻す処理が要る。代わりに DISPENSE 時に
在庫を再検証し、他取引と競合していれば 4001 で弾く。

### 4.2 入金

紙幣は一時保留部 (エスクロー) に収納済みとみなす。
`EJ(S) → 記帳 → 金庫収納 → EJ(E)`。
収納に失敗した場合は紙幣を返却し、記帳を取り消す。

### 4.3 振替 — 補償トランザクション

2 口座の更新を 1 つの原子的操作にできないため、次の順序をとる。

1. 相手口座を **先に** 読んで存在と受入可否を確認する
   (出金だけ成立して相手が居ない最悪ケースを構造的に排除)
2. 自口座を排他読み → 出金を確定
3. 相手口座を排他読み → 入金を確定
4. 3 が失敗したら 2 を打ち消す (補償)
5. 4 も失敗したら `RC-FATAL`。EJ に不整合を記録し係員対応とする

## 5. 検証順序 (`ATMPOST`)

順序を固定する理由は、利用者に返すエラーが端末や時刻でぶれないように
するため。上から評価し、最初に該当したものを返す。

| # | 検証 | エラーコード |
| --- | --- | --- |
| 1 | 金額が正・上限以内 | 3005 / 3002 |
| 2 | 営業時間内 | 3007 |
| 3 | 手数料算出 (時間帯別) | — |
| 4 | カード限度額 (1 回 → 当日額 → 当日回数) | 3002 / 3003 / 3004 |
| 5 | 口座状態 (解約 → 凍結 → 休眠) | 2003 / 2002 / 2004 |
| 6 | 支払可能残高 + 当座貸越枠 | 3001 |

手数料は限度額の判定対象に **含めない** が、残高からは差し引く。

この順序の所有者は `ATMPOST` である。`ATMACCT` は口座レコードと
技術リターンコードだけを返し、口座状態の判定はしない。READ の副作用と
して業務エラーを返すと、限度額より先に口座状態のエラーが出るなど、
順序が実装上ずれてしまうため。

千円単位の検証 (3006) は物理的な払出可否として `ATMCASH` が返す。
上表の金額検証 (1) が「いくらまで扱うか」、3006 が「その金額を紙幣で
組めるか」という役割分担になっている。

営業時間は既定で 00:00–24:00 (24 時間稼働) のため 3007 は発生しない。
時間規制を導入する際は `ATMPOST` の `WS-OPEN-HHMM` / `WS-CLOSE-HHMM`
を変える (本来は外部マスタ化すべき箇所)。

### 手数料 (曜日区分 × 時間帯 × カード区分)

手数料は時刻だけでは決まらない。実際の銀行は曜日区分と組み合わせる。
マスタ `data/atmfee.dat` に外部化し、`ATMPOST` が起動時に読み込む。

| 曜日区分 | 時間帯 | 出金 | 振込 |
| --- | --- | --- | --- |
| 平日 (W) | 00:00 – 08:44 | 110 円 | 220 円 |
| 平日 (W) | 08:45 – 17:59 | 0 円 | 110 円 |
| 平日 (W) | 18:00 – 23:59 | 110 円 | 220 円 |
| 土曜 (S) | 09:00 – 13:59 | 110 円 | 220 円 |
| 土曜 (S) | 上記以外 | 220 円 | 220 円 |
| 日祝 (H) | 終日 | 220 円 | 220 円 |

提携行カードは別体系 (平日・土曜 220 円、日祝 330 円)。

**平日・土曜が祝日にあたる場合は日曜・休日扱い**とする。この判定は
`ATMCAL` が一元的に行い、手数料も全銀システムの接続時間も同じ区分を
入力にとる。

## 6. 金種計算アルゴリズム (`ATMCASH`)

貪欲法は不成立ケースを取りこぼす。例えば 1 万円券が切れ、
2 千円券 5 枚と千円券が残る状態で 8,000 円を要求すると、
貪欲法は 5 千円券から取って 3,000 円の端数で行き詰まる。

そこで **有界ナップサック DP** で最小枚数解を厳密に求める。

```
状態  F(c, u) = カセット 1..c だけで u (千円単位) を構成する最小枚数
初期  F(0, 0) = 0,  他は ∞
遷移  F(c, u) = min { F(c-1, u - k·d(c)) + k }   (0 ≤ k ≤ avail(c))
復元  K(c, u) に採用した k を保存し、c = N から逆順に辿る
```

計算量は O(カセット数 × 金額単位数 × 枚数) = 最大 4 × 1001 × 枚数。
1 回の払出上限を 100 万円 (1000 単位) に制限しているため、
端末の応答時間に収まる。

**不成立時の理由分け**: 在庫総額が不足していれば 4001、
総額は足りるが組合せが作れなければ 4002 を返す。利用者への
案内文言が変わるため区別する必要がある。

障害中 (`F`) および空 (`E`) のカセットは在庫ゼロとして扱う。

## 6.5 認証方式と限度額

限度額はカードに焼き付けず、媒体と認証方式の組で持つ。

| 媒体 | 認証方式 | 1 回 | 当日累計 | 回数 |
| --- | --- | --- | --- | --- |
| 磁気 | 暗証番号のみ (P) | 50 万 | 50 万 | 10 |
| IC | 暗証番号のみ (P) | 50 万 | 50 万 | 10 |
| IC | オフライン PIN (O) | 100 万 | 200 万 | 10 |
| IC | 生体認証 (B) | 100 万 | 500 万 | 20 |

**そう分けた理由**: 実際の限度額は認証の強度で変わる。ゆうちょ銀行は
2026 年 8 月 17 日に、暗証番号のみの ATM 取引の 1 日あたり引出上限を
200 万円から 50 万円へ引き下げた。一方 IC カードと生体認証の組み合わせ
なら 500 万円まで設定できる。こうした改定は行政・防犯上の理由で起きる
ため、カードマスタに埋めると全件更新が必要になる。

カード個別の設定 (`CARD-LIMIT-*`) は「銀行が定める上限の範囲内で顧客が
下げられる」という位置づけで、実効値は両者の小さい方をとる。

磁気カードは JIS II 型 (国内独自、ストライプがカード表面)、IC は全銀協
IC キャッシュカード標準仕様 (EMV 準拠) で、両者は併存する。PIN の照合
場所が違う (磁気はホスト、IC はカード内) が、**PIN 不一致のエラーは
どちらも同じ 1005 を返す**。利用者にとっては同じ「暗証番号が違う」で
あり、認証技術の違いを画面に漏らす必要がないため。

## 6.6 他行あて振込 (全銀システム)

全銀システムは 2 階建てで、`ATMZGN` がこれを模擬する。

| 経路 | 条件 | 入金 |
| --- | --- | --- |
| コアタイム (C) | 平日 8:30–15:30 | 当日・即時 |
| モアタイム (M) | 上記以外で相手行が参加かつ接続時間内 | 当日・即時 |
| 翌営業日 (N) | 相手行が未参加または接続時間外 | 翌営業日 |

コアタイムは加盟行の接続が**義務**だが、モアタイム (2018 年 10 月稼働)
は**参加が任意**で、未参加行や接続時間を限定する行が残っている。即時
着金するかは自行と相手行の双方の接続時間に依存する。

**タイムアウトは「失敗」ではなく「成否不明」** である点が重要。電文が
相手行に届いていたかが判らないため、単純に引落を戻すと二重入金になる。
取消電文が通れば引落を戻し、取消も通らなければ `RC-FATAL` を返して
不確定取引として EJ に残し、日次突合と係員対応に委ねる。

突合の鍵になる **追跡番号は EJ に必ず残す**（`JRNL-TRACE-NO`）。
タイムアウト時にも `ATMZGN` が番号を返すのはこのため。取消電文は
同じ番号で送る（採番し直すと相手行が別取引とみなして取り消せない）。

## 6.7 日次締め (`ATMDAY`)

端末が停止している時間帯に流す。オンライン中に走らせると在庫と EJ が
動き続け、突合した瞬間の値が意味を持たない。

処理順序そのものに意味がある。

| # | 処理 | 備考 |
| --- | --- | --- |
| 1 | 締め状態の確認 → 実行中フラグ | 判定は `ATMCLS` が持つ |
| 2 | EJ 走査 → 不確定取引の抽出 | 取引単位に開始と終了を突合 |
| 3 | 現金の帳簿値と実査値の突合 | 判定は締め側、帳簿は `ATMCASH` |
| 4 | 帳票出力 | 整形は `ATMRPT`、判定はしない |
| 5 | 当日計のクリアと営業日繰越 | 検出がすべて終わってから |

**検出 (2)(3) を繰越 (5) より前に置く理由**: 繰越は当日計を消す。先に
消すと差異の原因が追えなくなる。

**二重実行を弾く理由**: 締めは営業日の取引を確定させる操作なので、
同じ日に二度流すと一度目に検出した差異が消えて追跡できなくなる。

**実行中フラグを自動解除しない理由**: 前回が異常終了してフラグが
残った場合、自動で解除すると多重実行を許してしまう。係員が原因を
確認してから `ATMCLS` の `RELEASE` で解除する。

中断状態を別に設けていないのは、書き込む前に落ちる以上フラグを
立てられず、意味を持たないため。実行中フラグが残っていること自体が
「前回が異常終了した」を表す。

### 実査していないことを黙らない

実査枚数の入力経路がまだ無い。ここで帳簿値を実査値として埋めると、
比較が必ず一致して差異ゼロになり、**実査していないのに「実施して
問題なし」と読める帳票**が出てしまう。

そのため未実施は未実施として扱い、突合そのものを行わず、帳票にも
「現金実査: 未実施」と明記する。係員操作パネルを作る際は
`READ-COUNTED-NOTES` で入力値を受け取るだけで、以降の突合が有効になる。

同じ理由で、検出件数が上限に達して明細を打ち切った場合は、件数が
ゼロでも要対応とする。記載漏れがある帳票を「問題なし」と読ませない。
係員対応の要否は締めの判断基準なので `ATMDAY` が決め、`ATMRPT` は
渡された結果を書くだけにする。

### EJ の突合方法

EJ は追記専用で、1 取引につき `S` (開始) と `E` (終了) を書く。
したがって **`S` があって `E` が無い取引は途中で落ちた取引**で、現金が
出たかどうかが判らない。これを不確定取引として抽出する。

EJ は時系列順なので、取引 ID をキーに保持して `E` が来たら降ろす、
という 1 パスで足りる。ソートは要らない。

集計は「終わった取引」だけを数える。途中で落ちた取引を売上に数えると
帳簿が合わなくなるため。

### 取引 ID の一意性

取引 ID とセッション ID は **`ATMCLS` の連番から採る**。連番は締め状態
ファイルに持つので、電源断や再起動をまたいで続く。用途の区別は前置
記号 (`T` / `SES`) で表す。

時刻とセッション内連番で作ると、連番がセッションごとに 1 へ戻るため、
同じ秒に始まった別セッションの取引と衝突する。締めバッチは取引 ID で
開始と終了を突き合わせるので、重複すると**別の取引を不確定として
誤検出する**。この不具合は実際に締めバッチを流して発覚した。

### 検出する事象

| 種別 | 内容 | 係員の対処 |
| --- | --- | --- |
| PN | 不確定取引 (`E` 欠落) | EJ と現金の実査で成否を判断 |
| ZU | 成否不明の他行為替 | 追跡番号で相手行へ照会 |
| CD | 現金の帳簿値と実査値の差異 | 実査のやり直しと原因調査 |
| RF | 取消が失敗したまま残った取引 | 手作業で勘定を戻す |

## 7. 排他制御

| 層 | 方式 | 目的 |
| --- | --- | --- |
| ファイル | `LOCK MODE IS MANUAL` + `READ WITH LOCK` | 他端末との競合排除 |
| レコード | `ACCT-VERSION` による楽観ロック | 悲観ロックが効かない環境への保険 |

二重防御にしているのは、ファイル共有方式 (NFS 等) によって
レコードロックが実質無効になる構成が現場に存在するため。
楽観ロックが不一致を検出した場合は `9002` (混雑) を返し、
利用者には再操作を促す。

`READLOCK → UPDATE` は同一モジュール呼出の中で完結させること。
間に他口座の I/O を挟むとロックが解放される。

## 8. 認証とカード閉塞

- 連続 PIN 誤り 3 回でカードを閉塞 (`CARD-STATUS = 'L'`)
- 閉塞済カードの再投入は即拒否し、上位へ取込指示を返す
- 存在しない PAN は再入力させず即終了する (総当たり対策)
- 有効期限は「当月末まで有効」
- 認証成功時、営業日が変わっていれば当日累計をゼロクリアする
  (日次バッチに依存しない自己修復方式)

PIN ハッシュは `ATMAUTH` の `CALC-PIN-HASH` SECTION が唯一の所有者。
外部からは `HASHPIN` 機能コード経由で呼ぶ (マスタ作成ユーティリティ
`ATMSEED` もこの経路を使う)。本番機で HSM の PIN ブロック検証へ
置き換える際も、変更はこの 1 箇所に閉じる。

> **注意**: 本実装のハッシュ式は学習用の簡易なものであり、
> 暗号学的強度を持たない。実運用には使用しないこと。

## 9. エラーコード体系

| 帯 | 分類 | 例 |
| --- | --- | --- |
| 1xxx | 認証・カード系 | 1005 暗証番号相違 / 1006 媒体非対応 |
| 2xxx | 口座系 | 2002 口座凍結 |
| 3xxx | 取引系 | 3001 残高不足 / 3003 当日限度額超過 |
| 4xxx | 現金機構系 | 4001 現金不足 / 4003 実査差異 |
| 5xxx | 他行接続系 | 5001 金融機関不明 / 5003 全銀タイムアウト |
| 6xxx | 締め運用系 | 6001 締め済み / 6002 締め実行中 |
| 9xxx | システム系 | 9002 混雑 / 9003 パラメタ未整備 |

帯は「原因の性質」で切る。実装担当やサブシステムで切らない。媒体系を
1xxx 内のサブ帯 (11xx) にしなかったのはこのため。カード系と同じ粒度で
あり、サブ帯を作る理由がない。

逆に他行接続は独立した帯にした。宛先不明・接続不能・応答なしが
まとまって発生し、係員の対処 (相手行への照会) も共通になるため。

翌営業日入金は **エラーではない**。正常終了として経路
(`ZGN-RT-NEXT-DAY`) と入金日で表す。正常系をエラーチャネルに載せると、
呼出元がそれだけを特例で除外することになり、経路が増えるたびに穴が
増えていく。

EJ にはコードを、画面には平易な文言を出す。対応表は
`ATMMAIN` の `SHOW-ERROR` にまとめてある。

## 10. 試験シナリオ

`make seed` で以下のデータが作られる。

| 口座 | 状態 | 残高 | 貸越枠 | カード | PIN | 1回限度 | 当日額 | 当日回数 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1000000001 | 正常 | 350,000 | 0 | …0001 | 1234 | 200,000 | 500,000 | 10 |
| 1000000002 | 正常 | 80,000 | 100,000 | …0002 | 9999 | 50,000 | 100,000 | 3 |
| 1000000003 | 凍結 | 500,000 | 0 | — | — | — | — | — |

カセット: 1万×300、5千×200、2千×5 (意図的に少数)、千×400。

確認できる主な経路:

1. 正常出金 → 金種明細と残高が表示される
2. 2,000 円券に依存する金額 → 在庫 5 枚の制約下で DP が解を探す
3. `…0002` で 60,000 円出金 → 3002 (1 回限度超過)
4. `…0002` で 4 回目の出金 → 3004 (当日回数超過)
5. 1000000002 から 150,000 円出金 → 貸越枠内なので成立し残高が負になる
6. 1000000003 へ振込 → 2002 (口座凍結) で相手確認の段階で弾かれる
7. PIN を 3 回間違える → カード閉塞、以後は 1004
8. 21 時以降に出金 → 手数料 220 円が残高から引かれる

## 11. 既知の制約

- 端末 1 台・単一プロセス前提。複数端末での同時実行は
  ファイルロックに依存するため、共有ファイルシステムの実装に左右される
- 振替は補償方式のため、補償失敗時に不整合が残り得る。
  真の原子性が必要ならトランザクションマネージャ (CICS 等) が要る
- 実査枚数の入力経路が無い。締めバッチは帳簿値をそのまま実査値と
  みなすため、現金差異 (CD) は常にゼロ件になる。係員操作パネルを
  作る際に `READ-COUNTED-NOTES` を差し替える
- カセット装填のバッチは未実装
- 通貨は JPY 固定。`ACCT-CURRENCY` は保持のみで判定には使っていない
- 入金は金種別計数機を持たない簡易機の想定。投入金額から金種を
  推定して在庫に加算するため、在庫の金種内訳が実物とずれ得る。
  金種別計数機を前提にするなら `CASH-PARM` に入金内訳を追加する
- EJ の採番は起動時に全件走査して復元する。日次でローテーション
  しない運用では、年数の経過とともに起動が線形に遅くなる
