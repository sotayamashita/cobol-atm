# 一般 ATM 仕様との対応と、未実装領域の契約

版数 1.0 / 2026-09-18

## 0. 本書の位置づけ

**`docs/design.md` が本プロジェクトの正である。** 本書はそれに従属する。

本書の役割は 3 つ。

1. 日本の銀行 ATM の一般的な構成と、本実装の選択を**対応付ける**
   （なぜ一般仕様どおりにしなかったのかを残す）
2. 一般仕様のうち**採用しなかったもの**と、その理由を記録する
3. **未実装領域**（§11 既知の制約）について、着手時に凍結すべき契約を先に置く

設計判断そのものは `design.md` に書く。本書に新しい判断を書かない。
両者が食い違った場合は `design.md` が優先する。

## 1. 一般的な ATM の階層構造と、本実装の位置

```
[ATM 実機]  ──専用線/VPN──  [対外系(ATMホスト)]  ──  [勘定系(元帳)]
    │                              │
    │                        [統合ATMスイッチング/MICS]
    │                              └── 他行・コンビニATM
    └ 制御部 + 周辺ユニット群
                               [全銀システム] ── 内国為替
                               [日銀ネット]   ── 最終決済
```

本実装がカバーするのは次のとおり。

| 一般構成 | 本実装 | 備考 |
| --- | --- | --- |
| ATM 制御部・取引順序制御 | `ATMMAIN` | コンソール 1 系統 |
| カード認証・PIN | `ATMAUTH` | PIN はローカルハッシュ照合 |
| 紙幣機構 | `ATMCASH` | PLAN / DISPENSE / ACCEPT |
| 電子ジャーナル | `ATMJRNL` | S / E / R レコード |
| **対外系 + 勘定系** | `ATMPOST` + `ATMACCT` | **ホストを持たずローカル元帳に畳んである** |
| 全銀システム | `ATMZGN` | コアタイム / モアタイム / 翌営業日を模擬 |
| 日次締め | `ATMDAY` + `ATMCLS` + `ATMRPT` | 端末停止中に実行 |
| 統合 ATM スイッチ (MICS) | — | 未実装 |
| 日銀ネット | — | 範囲外 |

**最大の構造差**: 一般の ATM は対外系を介してホストと電文をやりとりするが、
本実装はホストを持たず口座元帳を端末側の索引編成ファイルに置いている
(`design.md` §1)。したがって「ATM ↔ ホスト電文」という契約は**現時点では存在しない**。
対外電文が実在するのは `ATMZGN` の他行為替だけである。

## 2. 一般仕様との差分（採用しなかったもの）

初稿では業界一般の設計を前提に書いたが、本実装と矛盾するため取り下げた。
同じ提案が再び出たときに議論をやり直さないよう、理由を残す。

### 2.1 現金機構の 2 相コミット（エスクロー）

| | 一般的な ATM | 本実装 |
| --- | --- | --- |
| 出金 | `prepare`（エスクローへ繰出）→ `present`（提示）→ `confirmTaken` | `PLAN`（**計算のみ**）→ `DISPENSE`（一括） |
| 入金 | `count`（エスクロー計数）→ `commit`（金庫収納） | `ACCEPT`（計数結果を渡して一括収納） |

**採用しない。** 一時保留部そのものは概念として存在する
（`design.md` §4.2、収納失敗時に紙幣を返却できるのはこのため）が、
それを 2 つの機能コードに分けて呼出元へ露出させない。

分ければ「準備したまま確定も取消もされていない」状態が呼出元に生まれ、
電源断をまたいで復旧する責務も呼出元に移る。本実装は端末 1 台・単一
プロセスで、その状態を持ち越す先が無い。`ATMCASH` の中に閉じたまま
一括で成否を返すほうが、`ATMMAIN` の取引順序制御が単純になる。

`PLAN` はエスクローではない点に注意。在庫を押さえず金種構成を計算するだけで、
`DISPENSE` 時に在庫を再検証する（`design.md` §4.1「なぜ PLAN と DISPENSE を分けるか」）。
`CASHIF.cpy` のコメントどおり、呼出元は `PLAN` 結果を書き換えてはならない。

### 2.2 「現金を先に確保してから記帳する」入金順序

**採用しない。本実装は出金・入金とも記帳先行で統一されている。**

`ATMMAIN` の `TXN-DEPOSIT` は `POST-FN-DEPOSIT`（記帳）→ `CASH-FN-ACCEPT`（収納）
→ 失敗時 `REVERSE-POSTING` の順。出金の `WITHDRAW` → `DISPENSE` → `REVERSE` と同型。

一般的な ATM は「金庫へ収納したら返却できない」ため現金先行を採る。
本実装は収納を `ATMCASH` の中に閉じた一括操作にしているので、
呼出元から見れば「収納できたか」は 1 つの成否でしかなく、現金先行に
する利点が無い。記帳先行に揃えたほうが、取消経路 (`REVERSE-POSTING`)
を出金と共通化できる。

### 2.3 ISO 8583 風のメッセージ型・応答コード

**採用しない。** 本実装のエラーコード体系は `design.md` §9 の 4 桁帯
（1xxx 認証 / 2xxx 口座 / 3xxx 取引 / 4xxx 現金機構 / 5xxx 他行接続 /
6xxx 締め運用 / 9xxx システム）が正。`00` / `51` / `55` / `91` といった
外部体系を持ち込まない。

ただし後述 §3.1 の「成否不明」という**分類の考え方**だけは有効で、
これは既に `design.md` §6.6 に取り込まれている。

### 2.4 PIN ブロック（ISO 9564 / DUKPT）

**現時点では採用しない。** PIN 照合は `ATMAUTH` の `CALC-PIN-HASH` が唯一の所有者で、
外部からは `HASHPIN` 機能コード経由で呼ぶ（`design.md` §8）。
HSM の PIN ブロック検証へ置き換える際も変更はこの 1 箇所に閉じるため、
先回りして I/F を暗号仕様に寄せる必要がない。

> `design.md` §8 の注記どおり、現行ハッシュ式は学習用で暗号学的強度を持たない。

### 2.5 ジャーナルのハッシュ連鎖

**未採用（将来検討）。** 一般の ATM は制御部の電子ジャーナルとは別に
紙幣処理部にも入出金ログを持ち、両者を突合して不正出金を検知する。

本実装の EJ は追記専用の順編成で、改竄検知機構を持たない。
突合は「EJ の `S`/`E` 対応」と「現金の帳簿値と実査値」の 2 軸で行う
（`design.md` §6.7）。実査入力経路が未実装なので、後者は現状機能していない。

### 2.6 通帳記帳機 (PBPR)・係員操作パネル

`design.md` §1 で**範囲外**と宣言済み。並列作業の候補に数えない。

## 3. 一般仕様から引き継ぐ考え方（本実装に既にあるもの）

### 3.1 結果の 3 分類 — 成功 / 失敗 / **成否不明**

対外通信を伴う処理では、結果を 2 値で扱ってはならない。

| 分類 | 本実装での現れ方 | 端末の扱い |
| --- | --- | --- |
| 確定成功 | `RC-OK` | そのまま完了 |
| 確定失敗 | 3001 残高不足 / 1005 暗証番号相違 など | 記帳されていないと断定してよい |
| **成否不明** | 5003 全銀タイムアウト | 取消電文で解決。取消も通らなければ `RC-FATAL` |

`design.md` §6.6 が「タイムアウトは失敗ではなく成否不明」として既に規定している。
単純に引落を戻すと二重入金になるため。

**この分類を新しい対外接続（MICS、将来のホスト）へ拡張する際も同じ扱いにする。**

### 3.2 取消電文は同一の追跡番号で送る

採番し直すと相手行が別取引とみなして取り消せない（`design.md` §6.6）。
`JRNL-TRACE-NO` は成否不明時にも必ず EJ に残る。

### 3.3 取引 ID は電源断をまたいで一意

`ATMCLS` の連番から採る（`design.md`「取引 ID の一意性」）。
セッション内連番で作ると締めバッチが別取引を不確定として誤検出する。

一般の ATM が `txnId` を「機関 + 端末 + 営業日 + 連番」で構成し冪等キーに使うのと
同じ狙いだが、本実装はホストを持たないので冪等応答の相手がいない。
現時点での用途は**締めバッチでの `S`/`E` 突合**に限られる。

### 3.4 不確定取引は自動判定しない

EJ に `S` があって `E` が無い取引は、現金が出たか判らない。
自動で成功／失敗を決めず、`PN` として抽出し現金実査で確定させる
（`design.md` §6.7「EJ の突合方法」）。

同じ理由で、実査が未実施なら突合そのものを行わず帳票に「未実施」と明記する。
**実施していないものを「問題なし」と読ませない**という原則は、
一般の ATM 運用でも同じ。

## 4. 未実装領域で、着手時に凍結すべき契約

`design.md` §11 の既知の制約に対応する。ここに書いたのは**契約案**であり、
実装着手時に `design.md` へ昇格させる。

### 4.1 現金実査の入力経路

現在の最大の穴。これが埋まるまで現金差異 (CD) は常にゼロ件になる。

凍結すべきもの:

| 項目 | 契約案 |
| --- | --- |
| 入力先 | `ATMDAY` の `READ-COUNTED-NOTES` を差し替える（既に分離済み） |
| 入力単位 | カセット 4 本それぞれの実枚数 |
| 未実施の表現 | 「ゼロ枚」と「未入力」を**別の値**にする。同一視すると全額差異として誤検出する |
| 突合の主体 | 判定は `ATMDAY`。`ATMCASH` は `THEORY` で帳簿値を返すだけ（現行どおり） |
| 帳票 | 未実施なら突合を行わず「現金実査: 未実施」と明記（現行どおり） |

### 4.2 入金の金種別計数 — **実装済み (2026-09-18)**

決着した内容は `design.md` §4.2 にある。着手前の契約案からの変更点だけ残す。

| 項目 | 契約案 | 実装 |
| --- | --- | --- |
| I/F | `CASH-PARM` に入金内訳を追加 | `CASH-IN-DEPOSIT`（金種 × 枚数）として追加 |
| 既定 | 内訳未設定なら推定へフォールバック | **フォールバックを設けず推定を削除した** |
| リジェクト | 返却枚数も返す必要がある | **不要だった** |

**推定へのフォールバックを設けなかった理由**: `ATMMAIN` が常に内訳を渡す
ため、フォールバック経路に入る呼出元が存在しない。残せば検証されない
分岐が 1 つ増えるだけで、しかもそこを通ると在庫がずれるという、
まさに直したかった不具合が復活する。機械の想定を「金種別計数機を持つ」
一本に決めた。

**返却枚数が不要だった理由**: 内訳は収納した紙幣だけを表す。返却した
紙幣は最初から内訳に含まれないので、在庫を合わせるうえで返却枚数を
知る必要がない。利用者への返却は物理動作であり、帳簿には現れない。

### 4.3 カセット装填バッチ — **実装済み (2026-09-18)**

決着した内容は `design.md` §6.8 にある。契約案は 3 項目とも変更なく実装した
（実行条件・EJ への記録・責務の分離）。着手後に決めた点だけ残す。

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 加算か置換か | **置換**（装填後の枚数を設定） | 装填は現物の差し替え。加算にすると帳簿と現物のずれが温存される |
| 空入力とゼロ | **別物として扱う** | 空＝触らない、ゼロ＝空のカセットに差し替えた。同一視すると事故になる |
| 障害状態 (`F`) | **差し替えたカセットは引き継がない** | 障害は現物に付く状態で、現物が変われば付いてこない |
| 金種の変更 | **できない**（`4005` で弾く） | 金種の降順は払出 DP の前提。変更は装填ではなく据付の作業 |

### 4.4 営業時間の外部マスタ化 — **実装済み (2026-09-18)**

契約案の 3 項目（順編成・不在時は規制なし・`ATMCAL` の区分）はそのまま実装した。
`atmhour.dat` / `HOURREC.cpy`。決着した内容は `design.md` §5 にある。

着手後に決めた点: **該当区分の行が無い場合も規制なし**として扱う。
「設定していない」を「終日休止」と解釈すると、マスタの整備漏れで端末が
全面停止する。終日休止は 0000–0000 を明示的に入れて表す。

### 4.5 将来のホスト接続

`design.md` §1 が「ホスト接続へ移行する場合は `ATMACCT` の差し替えだけで済む」
としている。移行時に凍結すべきもの:

| 項目 | 契約案 |
| --- | --- |
| 差し替え境界 | `ATMACCT`（`ACCTIF.cpy`）のみ。`ATMPOST` の検証順序は変えない |
| 業務判定の所在 | 引き続き `ATMPOST`。ホストが業務エラーを返しても、それを技術 RC に写して渡す |
| 楽観ロック | `ACCT-VERSION` はホスト側の排他に置き換わる。`9002`（混雑）の意味は維持する |
| 結果の分類 | §3.1 の 3 分類を適用。ホスト無応答は「失敗」ではなく「成否不明」 |
| 取消 | 原取引が存在しなくても取消を成功として扱えること（端末は記帳の有無を知らない） |

## 5. 残作業の並列着手可能性

`design.md` §11 の制約を、依存関係で整理したもの。

### 独立して着手できる

| # | 作業 | 依存 |
| --- | --- | --- |
| 1 | 装填バッチでのカセット状態表示 | なし。ただし `THEORY` の出力拡張を伴う |

§4.1 を除く未実装項目は 2026-09-18 に完了した。

| 項目 | 状態 |
| --- | --- |
| §4.1 現金実査の入力経路 | **未着手**（係員操作パネルが範囲外のため保留） |
| §4.2 入金の金種別計数 | 完了 |
| §4.3 カセット装填バッチ | 完了 |
| §4.4 営業時間の外部マスタ化 | 完了 |
| 入金内訳のカセット状態検証 | 完了（障害中のカセットには収納しない） |
| 退避 EJ の保存年限管理 | 完了（`ATMPURGE`。保存年限は実行時指定） |

### 先行条件がある

| # | 作業 | 先行条件 |
| --- | --- | --- |
| 5 | 現金実査の入力経路 (§4.1) | 係員操作パネル（範囲外）か、代替の入力手段の決定 |
| 6 | 現金差異 (CD) の実効化 | 5 |
| 7 | ホスト接続 (§4.5) | 4.5 の契約凍結 |
| 8 | 複数端末対応 | 排他制御方式の再検討（`design.md` §7・§11） |

### 並列にできない

- 振替の真の原子性 — トランザクションマネージャ (CICS 等) の導入が前提で、
  補償方式を前提にした `ATMPOST` の構造ごと変わる
- 多通貨 — `ACCT-CURRENCY` の判定導入は手数料・限度額・金種計算の全てに波及する
